# ADR 0001：采用“宿主 + M3 编辑器岛”作为 MVP 架构

- **状态：** 已接受
- **日期：** 2026-11-05
- **决策者：** 架构组
- **相关：** SRS-M3STUDIO-001 V4.1 §0.2、§2.2、§6.4、§11 M2

## 背景

`prd-diy` 已有成熟的 REST 服务、隔离存储、版本治理、AI 编排与导出；前端是原生 DOM 画布。`m3e-canvas` 是 Next.js + React 的 M3 设计器，拥有 36 种语义部件、主题系统、Tidy、预览与 Prompt 生成。

直接 `git merge` 不可行：

- 两套前端运行时不同（原生 DOM vs React/Next.js）。
- 两套设计模型不同（任意节点树 vs `Item/Group/Frame`）。
- 两套导航模型不同（节点内 action vs 独立 FlowEdge）。
- 两套存储与版本语义不同。

## 决策

MVP 采用 **宿主应用 + M3 编辑器岛**：

1. 宿主继续负责项目、屏幕元数据、版本、锁定、权限、AI、关联、导出。
2. 编辑器岛是一个独立构建的 M3 编辑器页面，通过 `postMessage` 与宿主通信。
3. 宿主向岛下发 `ScreenDoc`、主题、设计 token、只读/锁定状态；岛只负责单屏编辑与预览请求。
4. 岛不直接访问 API，不直接落库，不持有项目级权限。
5. 岛的产物通过桥接协议回到宿主，由宿主做 schema 校验、`base_version` 冲突检查和版本写入。

## 备选方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 直接合并为统一 React 前端 | 暂不采用 | 需重写现有画布、编辑态注入、导出与全部回归测试，M1–M2 风险过高 |
| 用 iframe 嵌入整个 m3e-canvas 应用 | 不采用 | 两个应用各自管理项目与存储，无法满足单屏隔离与 FlowEdge 真源 |
| 把 M3 部件渲染器移植进原生前端 | 不采用 | 36 种部件与主题系统工作量大，且会形成第二套渲染实现 |
| 宿主 + 编辑器岛 | **采用** | 复用 M3E 设计能力，同时保留宿主治理与隔离；边界清晰，可独立测试 |

## 后果

**正面**

- M0 可用纯 Node 模块验证数据契约与桥接状态机，不引入 React 依赖。
- 宿主与岛可独立发布；岛崩溃不会破坏已保存版本。
- 后续若统一前端，可保留桥接协议与 `ScreenDoc` 契约，迁移成本可控。

**负面 / 代价**

- 需要维护协议版本、超时、重连、草稿保留与安全校验。
- 编辑器/预览/导出必须共享渲染契约，否则会出现“编辑所见非导出所得”。
- 岛内不能直接做跨屏操作，关联与预览需回宿主编排。

## 约束

- 协议固定为 `m3studio/editor@1`，所有消息带 `protocol/request_id/screen_id`。
- 宿主必须校验 `event.origin` 与 `event.source`。
- 单条消息上限 5MB；大文档走宿主侧分片或文件通道（M1 细化）。
- 岛不得接收项目级密钥、其他屏幕正文或成员权限数据。

## 验证

- `tests/m3-editor-bridge.test.mjs` 覆盖协议校验、状态机、冲突、超时、重试与安全校验。
- `docs/编辑器岛桥接协议.md` 为协议唯一说明。

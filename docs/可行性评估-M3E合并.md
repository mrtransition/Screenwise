# 可行性评估：`prd-diy` × `m3e-canvas` 产品级合并

- **评估编号：** FEA-M3STUDIO-001
- **版本：** V1.1
- **日期：** 2026-11-05
- **对应需求：** SRS-M3STUDIO-001 V4.1
- **结论：** **有条件 Go**（按 M0–M4 分阶段，先验证数据与编辑器边界，再投入 AI 与导出）

---

## 1. 评估摘要

合并的目标不是把两个仓库拼在一起，而是把两条能力链合成一条：

> 想法 → AI 逐屏生成 / 手工搭屏 → 主题统一 → 屏幕关联 → 可点击预览 → 版本治理 → 导出可运行原型 + 可交付给编码 Agent 的 Prompt。

**技术可行性：高。** 两侧核心能力都已存在，M0 已用纯 Node 跑通：

- M3E `Doc` ↔ `ScreenDoc` 往返守恒；
- `action/actions/frame.swipe` ↔ `FlowEdge` 投影；
- 自由组坐标、隐藏字段、动态孤儿边；
- 编辑器桥接协议与状态机；
- 36 种 kind 白名单与 schema 校验。

**产品可行性：中高。** 主要风险不在 AI，而在：

1. 两套设计模型与坐标模型的语义差异；
2. 编辑器/预览/导出的渲染一致性；
3. 旧 `node-tree` 文档的只读兼容；
4. 主题、版本、FlowEdge 三套历史的边界；
5. 团队服务器模式的权限模型。

**不建议直接 `git merge`。** 两侧运行时、数据模型、存储与版本语义均不同，直接合并会产生双真源与不可控回归。

## 2. 现状盘点

### 2.1 `prd-diy` 强项

| 能力 | 现状 | 合并后价值 |
| --- | --- | --- |
| 三层隔离 | 存储/上下文/编辑隔离，已有测试 | 保证 A 屏操作不触碰 B 屏 |
| 版本治理 | 单屏完整快照、回滚、锁定、权限 | 支撑 M3 编辑与 AI patch |
| AI 编排 | 生成、patch、路由、内置生成器、模型目录 | 继续作为差异化能力 |
| 关联与预览 | FlowEdge 独立存储、孤儿边、静态导出 | 与 M3E 手势/预览合并 |
| 零运行时依赖 | Node ≥20，原生 HTTP/存储 | 降低部署与合并复杂度 |

### 2.2 `m3e-canvas` 强项

| 能力 | 现状 | 合并后价值 |
| --- | --- | --- |
| 36 种 M3 部件 | `KIND_SPEC`、尺寸、变体、slot | 设计表达力 |
| 主题系统 | palette、dark、contrast、shape、font、motion | 项目级统一视觉 |
| Tidy / 连接组 / 自由组 | 布局与图层 | 手工搭屏效率 |
| 预览与分享 | 点击/滑动预览、分享链接 | 可点击原型 |
| Prompt 生成 | vibe-coding Prompt、agent.md | 第二交付物 |
| i18n / AI 辅助 | 多语言与设计辅助 | 体验补齐 |

### 2.3 关键差异

| 维度 | `prd-diy` | `m3e-canvas` | 合并策略 |
| --- | --- | --- | --- |
| 设计模型 | 任意 `node-tree` | `Item/Group/Frame` | 以 M3 语义模型为主，旧树只读 |
| 单屏边界 | 屏目录 + 版本 | 一个 frame | `ScreenDoc` |
| 导航 | 独立 FlowEdge | `item.action`/`frame.swipe` | FlowEdge 真源 + 投影 |
| 主题 | 项目级 design_tokens | 项目级 theme | 项目级 theme + 版本快照 |
| 前端 | 原生 DOM | Next.js/React | 宿主 + 编辑器岛 |
| 存储 | JSON 文件 + 原子写 | 浏览器本地/分享链接 | 宿主文件存储为权威 |
| 版本 | 单屏快照 | 无服务端版本 | 保留宿主版本模型 |

## 3. 方案对比

| 方案 | 描述 | 工作量 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 直接合并仓库 | 把 m3e-canvas 代码并入，统一构建 | 极高 | 极高：运行时/模型/存储冲突 | 否决 |
| B. 统一 React 前端重写 | 用 React 重写宿主前端 + M3 编辑器 | 高 | 高：回归面大，周期长 | 暂缓（M6 评估） |
| C. 宿主 + 编辑器岛 | 宿主保留治理，岛负责单屏编辑 | 中 | 中：协议/渲染一致性 | **MVP 采用** |
| D. 仅做导入导出 | 不嵌入编辑器，只做格式互转 | 低 | 低，但产品价值不足 | 否决 |
| E. 双前端并存但不互通 | 各自独立 | 低 | 数据割裂 | 否决 |

**选择 C 的理由：**

- 复用 M3E 的 36 部件、主题、Tidy、预览与 Prompt；
- 保留宿主的隔离、版本、权限、AI 与导出；
- 边界可用协议与 schema 测试，不需要一次性重写；
- 后续若统一前端，`ScreenDoc` 与桥接协议仍可复用。

## 4. 工作量估算

以 1 名全栈 + 1 名前端为主，按 M0–M6：

| 阶段 | 内容 | 估算 | 关键依赖 |
| --- | --- | --- | --- |
| M0 | 规格、ADR、数据模型 spike、桥接 spike、Registry、渲染契约 | 已完成（约 3–5 人日） | 无 |
| M1 | ScreenDoc/ProjectDoc 存储、schema、迁移、API、备份、旧格式只读、大文件导入 | 8–12 人日 | M0 契约冻结 |
| M2 | 编辑器岛集成、保存/版本/锁定/只读、图层、自由组、缩略图、渲染契约 | 10–15 人日 | M1 API + 岛构建 |
| M3 | M3 上下文、AI 输出契约、归一化、patch、路由、swipe 剥离 | 8–12 人日 | M1 schema + M2 编辑 |
| M4 | FlowEdge 投影、swipe、动态 orphan、预览、静态原型、Prompt、Prompt 包 | 8–12 人日 | M2 + M3 |
| M5 | P1：分享链接、协作、多语言、手势预览、更多 Tidy | 6–10 人日 | M4 |

**最大不确定性：**

- 编辑器岛与宿主的构建/部署方式（同源静态托管 vs 独立域名）；
- 渲染一致性（编辑器/预览/导出三处）；
- 旧 `node-tree` 只读渲染的覆盖度；
- 团队服务器模式的最小鉴权。

## 7. 共享渲染契约与视觉回归基线

### 7.1 共享契约（FR-RENDER-001～006）

| 编号 | 契约 | 验收 |
| --- | --- | --- |
| FR-RENDER-001 | 编辑器、预览、导出使用同一 `ScreenDoc → 视觉树` 映射 | 同一 doc 三处结构一致 |
| FR-RENDER-002 | 36 kind 的尺寸、圆角、变体、slot 由 Registry 唯一决定 | Registry 变更三处同步 |
| FR-RENDER-003 | 主题角色解析只走项目主题；屏幕仅 `frame.bg` 覆盖 | 无硬编码色值 |
| FR-RENDER-004 | 旧 `node-tree` 只读渲染与 M3 渲染隔离，不互相降级 | 旧项目可读且不写回 |
| FR-RENDER-005 | 自由组/连接组坐标计算使用同一 `layoutOf` 规则 | 位置偏差 ≤1dp |
| FR-RENDER-006 | 导出静态包不依赖运行时框架，交互由内联数据驱动 | 离线打开可跳转 |

### 7.2 视觉回归基线

- **基准设备：** 412×892（phone）、1280×800（desktop）。
- **基准主题：** 默认 purple、light、standard contrast、rounded、roboto。
- **基准屏幕：** `tests/fixtures/m3e-sample.json` 导入后的 4 屏（含未放置屏）。
- **比对方式：** 结构快照（DOM/视觉树）+ 关键尺寸断言；M2 起补截图 diff。
- **容差：** 坐标/尺寸 ±1dp；文本宽度以 `measurements.json` 为缓存，不作为唯一依据。
- **门禁：** 任何 kind 的尺寸/圆角/变体变化必须更新 Registry 与基线，并在 PR 说明。

## 9. Kill Criteria（停止或回退条件）

出现以下任一情况，应暂停合并并回退到“仅导入导出”方案：

1. **M1 结束仍无法保证单屏隔离**：改 A 屏会触碰 B 屏文件或版本。
2. **M2 结束编辑器/预览/导出三处渲染偏差 >2dp 且无法收敛**。
3. **M2 结束自由组坐标往返丢失 >1% 或不可逆**。
4. **M3 结束 AI 输出仍可绕过 schema 写入 action/跨屏内容**。
5. **M4 结束导出包无法离线打开或跳转错误率 >1%**。
6. **团队服务器模式无法在 M4 前提供最小鉴权**，导致越权写入。
7. **旧 `node-tree` 项目无法只读渲染**，导致存量用户数据不可访问。
8. **性能不可接受**：50MB 导入超时/崩溃，或编辑器加载 >5s（本地）。

回退策略：

- 保留 `ScreenDoc` 与 `FlowEdge` 契约，关闭编辑器岛，仅提供 M3E 导入/导出与只读预览；
- 旧项目继续走 `node-tree` 只读路径；
- AI 继续使用旧 `node-tree` 生成，不写 M3 模型。

## 10. 结论

**有条件 Go。**

- M0 已完成，数据模型与桥接协议可运行、可测试。
- M1–M4 是主战场，风险集中在渲染一致性与旧格式兼容，不在 AI。
- 建议按里程碑推进，每个阶段以 P0 验收项为门禁；未达门禁不进入下一阶段。
- 若触发 Kill Criteria，回退到“导入导出 + 只读预览”，保留后续重新立项空间。
